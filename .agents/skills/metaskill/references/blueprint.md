# New-harness blueprint

Resolve these fields from user intent and repository evidence. Ask only for material unknowns.

| Field | Question the design must answer |
|---|---|
| Goal | What repeated outcome should this harness make safer or cheaper? |
| Non-goals | What adjacent work must it deliberately not own? |
| Projects | Which independent repositories or project types will it route? |
| Recurring work | Which procedures are already expected to repeat? |
| Development | Which behavior requires specs, tests, reviews, or generated artifacts? |
| Deployment | Which services may receive builds, and what wording authorizes publication? |
| Secrets | Which systems own values, and which metadata may be recorded? |
| Irreversible actions | Which actions require an immediate confirmation or explicit opt-in? |
| Evidence | What observable result proves local, remote, build, deploy, and release states? |
| Capabilities | Which approved external or local seed skills are needed now? |

Start with core skills only. A stack name is not evidence that every related tool will be used. Add a capability when the stated goal or existing repository requires it.
